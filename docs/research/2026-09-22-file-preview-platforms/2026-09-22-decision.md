# WebTerm 文件预览平台选型结论

## 决定

不要用任何候选项目替换 WebTerm 文件管理器。保留现有远程 SFTP、标签分栏、草稿/冲突和持久化边界；在右侧编辑区增加“预览模式”。

`open-file-viewer` 是本轮最合适的**预览容器候选**，不是文件管理器候选：MIT、React 原生适配、插件与回退路径清晰，且覆盖面很广。但其 README 明确把复杂 Office/CAD/专有格式的高保真留给专用引擎或服务端转换，因此不能把它的格式表当作生产保真承诺。

## 推荐的分层

1. 默认、低风险：文本/代码继续 CodeMirror；图片、音视频走浏览器；PDF 使用 PDF.js；DOCX 使用 docx-preview；XLSX/CSV 使用 SheetJS 数据解析加虚拟表格。所有重组件按扩展名动态加载。
2. 统一体验：以 Open File Viewer 包装已验证的插件（首先 PDF、图片、媒体、文本、DOCX/XLSX），并保留 WebTerm 自己的下载、刷新、权限、关闭和标签交互。
3. 广格式按需开启：若确实需要 WPS、OFD、邮件、压缩包、CAD/3D 等，独立部署 kkFileView（Apache-2.0）为**只读、隔离、可关闭**的转换/预览服务；不嵌入其文件管理 UI，也不让其拿到长期 SFTP 凭据。
4. 只有在“需要多人高保真编辑 Office”成为明确需求时，另立项目评估 ONLYOFFICE。它是完整协同编辑服务（AGPL-3.0），需要 WebTerm 提供临时 HTTP 文件 URL、save callback、JWT/权限和至少独立的资源容量；不应作为普通预览功能的依赖。

## 候选对比（采样于 2026-09-22）

| 候选 | 星标 / 许可证 | 最适合 | 关键限制 | 对 WebTerm 的决定 |
|---|---:|---|---|---|
| Open File Viewer | 1,773 / MIT | 多格式、统一 React 预览容器 | 新兴；复杂格式不保证高保真 | **采用为可选预览壳** |
| PDF.js | 53,929 / Apache-2.0 | PDF 的稳定、高性能预览 | 只解决 PDF | **直接采用** |
| docx-preview | 2,097 / Apache-2.0 | DOCX 浏览器端只读预览 | HTML 能力限制，非 Office 编辑器 | **直接采用，标注保真边界** |
| SheetJS CE | 36,346 / Apache-2.0 | XLSX/CSV 数据解析 | 不是现成的像素级表格预览器；源码已迁移 | **采用解析层，不做 UI 依赖** |
| kkFileView | 14,722 / Apache-2.0 | 预览格式最广的独立服务 | Spring Boot + JDK 21 + LibreOffice，攻击面与运维成本显著 | **只做隔离式按需兜底** |
| ONLYOFFICE Docs | 6,922 / AGPL-3.0 | Office 高保真、协同编辑 | 重服务、集成与许可要求 | **暂不纳入预览一期** |
| Collabora Online | 3,349 / copyleft 生态 | LibreOffice 协同编辑 | GitHub 仅 Issue/发布，开发在 Gerrit；也属重服务 | **不优先** |

## 实施前验收门槛

- 增加受鉴权、一次性、短 TTL 的远程文件预览票据；PDF 必须支持 Range，不能把大文件塞进 WebSocket 或浏览器内存。
- 预览读取和下载与保存分离：预览永不写回，原有版本冲突确认仍只在文本编辑器内发生。
- 复杂文件只送入无网络出站、非 root、只读挂载/短生命周期的转换容器；文件大小、页数、解压比、CPU/内存/超时均限额。
- 以真实远端样本做兼容矩阵：10 万行文本、100 MB PDF、含图片的 DOCX、5 万行 XLSX、损坏/加密/压缩炸弹文件；每种都验证取消、关闭、断线与内存回收。

## 反证与结论强度

- 如果真实样本主要是工程 CAD、WPS/OFD 或遗留 Office，浏览器优先路线不足，应把 kkFileView 隔离服务提前到一期。
- 如果需要共同编辑 Office 而非预览，ONLYOFFICE/Collabora 的价值会超过上述轻量方案；这将是新的授权、存储回调与运维项目。
- 星数不能证明格式保真或安全。此结论以项目官方格式/架构说明和当前仓库状态为依据，最终采用前仍需用 WebTerm 的受控远端样本做 POC。
